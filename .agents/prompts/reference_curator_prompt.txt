# 3. Reference 的定位

`reference/` 是快速选型和风险检查资料，不是完整教材，也不是论文代写素材。

每份文档应帮助主 Agent 快速回答：

1. 这个方法适合解决什么问题？
2. 它不适合什么问题？
3. 核心数学思想是什么？
4. 需要满足哪些假设？
5. 输入和输出是什么？
6. 应如何验证结果？
7. 华为杯中常见的正确用法是什么？
8. 最常见的误用是什么？
9. Python 中通常使用什么可靠工具实现？
10. 进一步核查应阅读哪些权威来源？

不得把“算法名字多”当作知识库质量高。

# 6. 每个方法文件的统一模板

文件名使用清晰的英文小写 snake_case，例如：

```text
random_forest.md
missing_values.md
multiobjective_optimization.md
```

标题使用：

```markdown
# 随机森林（Random Forest）
```

每个文件尽量控制在约 800—1600 个中文字符；复杂方法可略长，但避免写成教材。

统一结构：

```markdown
# 方法中文名（English Name）

## 1. 适用问题

## 2. 不适用或需谨慎的情况

## 3. 核心思想

## 4. 基本数学形式

## 5. 输入、输出与主要假设

## 6. 标准建模流程

## 7. 评价与验证方式

## 8. 优点

## 9. 局限

## 10. 华为杯常见用法

## 11. 常见误用

## 12. Python 实现建议

## 13. 权威参考
```

要求：

- 数学公式使用标准 Markdown LaTeX；
- 只给必要公式；
- Python 部分只说明常用库和关键注意事项，不需要长篇代码；
- 说明 Baseline 和更复杂方法之间的关系；
- 明确写出方法选择的前提；
- 不写“该方法精度高、效果好”这类无条件结论。

# 7. README 索引要求

创建或更新：

```text

```

README 不应只是文件列表，还应提供按问题类型检索的方法导航。

## 目录导航

按分类链接到各子目录。

## 按任务类型选型

例如：

| 问题特征 | 首选 Baseline | 可考虑的升级 | 必做验证 |
|---|---|---|---|
| 连续变量预测 | 线性回归 | RF / GBDT / 神经网络 | 交叉验证、残差分析 |
| 季节性时间序列 | 季节朴素法、指数平滑 | SARIMA、状态空间 | 滚动回测 |
| 资源分配 | 线性规划 | MILP、多目标优化 | 可行性与敏感性 |
| 无监督分群 | K-Means | DBSCAN、层次聚类 | 稳定性与解释性 |

## 常见错误提醒

至少提醒：

- 不先做 Baseline；
- 数据泄漏；
- 测试集调参；
- 无依据堆叠算法；
- 用 AHP/熵权/TOPSIS 代替真实机制；
- 用启发式算法掩盖可精确求解的问题；
- 没有验证优化方案；
- 把相关性写成因果。

README 中的链接必须使用相对路径。

# 9. 内容质量规则

## 9.1 选型必须有条件

错误示例：

> XGBoost 通常比随机森林更准确。

正确示例：

> 对结构化表格数据，若存在非线性和特征交互，梯度提升树常是值得比较的候选；但仍应通过统一数据切分和交叉验证与线性模型、随机森林等 Baseline 公平比较。

## 9.2 明确假设和边界

例如：

- 线性回归需检查线性关系、残差和共线性；
- ARIMA 需要关注平稳性和时间依赖；
- K-Means 偏好近似球状、尺度可比的簇；
- TOPSIS 的结果依赖指标、归一化和权重；
- 遗传算法不能自动证明所得结果为全局最优。

## 9.3 强调验证

每个方法必须说明至少一种合理验证方式。

例如：

- 预测：交叉验证、滚动回测、残差分析；
- 聚类：稳定性、轮廓系数、业务解释；
- 优化：可行性检查、下界/上界、敏感性、与简单策略比较；
- 仿真：参数校准、重复模拟、置信区间；
- 评价模型：权重敏感性、排序稳定性。

## 9.4 不机械推荐复杂方法

文档应说明：

> 何时简单模型已经足够，何时才值得升级。
