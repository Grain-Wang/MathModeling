# Optimization Protocol — 华为杯数学建模阶段优化协议

> 本协议规定主 Agent 在 S2、S3、S4 中如何进行证据驱动、受时间约束的优化，以及 Reviewer 在 G2、G3、G4 中如何验收。它不是第三个常驻 Agent 角色。

---

## 1. 目的

优化不是随时换模型，而是在固定节点针对当前最重要的不确定性做有限改进：

\[
\text{正确性} > \text{全题闭环} > \text{可验证性} > \text{可复现性} > \text{性能} > \text{复杂度}
\]

禁止为了“更高级”而增加无证据、无时间边界或无法验证的复杂度。

---

## 2. 适用角色与权责

### Main Agent

负责发现瓶颈、提出候选改进、比较收益与成本、执行获准的改进，并保存优化报告。

### Reviewer Agent

负责检查优化是否有证据、是否受时间约束、是否有成功与停止条件，以及是否允许进入下一 Gate。Reviewer 不替主 Agent 改模型或代码。

### Strong-model Advisor（可选）

可在 O1、O2、O3 作为临时战略顾问使用，只提供独立意见，不接管项目、不直接修改成果，也不能替代 Gate 判定。

---

## 3. 强制优化节点

| 节点 | 所属阶段 | 核心问题 | 强制产物 | 提交 Gate 的允许决策 |
|---|---|---|---|---|
| O1 | S2 | 总体方案是否正确、简洁、可执行？ | `work/optimization/o1_solution_optimization.md` | `PROCEED_TO_G2` |
| O2 | S3 | Baseline 真正失败在哪里，S4 最值得改什么？ | `work/optimization/o2_baseline_diagnosis.md` | `PROCEED_TO_G3` |
| O3 | S4 | 继续优化是否值得，是否应冻结？ | `work/optimization/o3_freeze_decision.md` | `FREEZE_CANDIDATE` |

主 Agent 在相应阶段必须先读取本协议、完成对应报告，再提交 G2、G3 或 G4。

Reviewer 在对应 Gate 必须读取本协议和对应报告。报告缺失、证据不足或决策不满足上表时，不得给出 PASS。

---

## 4. 通用优化流程

每个节点必须按以下顺序进行：

```text
确认当前 Gate、剩余时间和已批准成果
→ 用数据、代码、日志或模型合同定位瓶颈
→ 提出少量候选改进
→ 比较收益、论文价值、验证性、时间、风险和回退成本
→ 只选择最有价值的动作
→ 设置时间盒、成功标准、停止条件和回退版本
→ 执行或形成冻结决定
→ 写入对应优化报告
```

不得先决定换模型，再事后寻找理由。

---

## 5. 证据等级

优化判断使用以下状态：

- `VERIFIED`：由当前项目中的数据、实验、代码或明确题目条件直接支持；
- `SUPPORTED`：有较强仓库证据，但仍含合理推断；
- `HYPOTHESIS`：尚待验证的假设；
- `UNKNOWN`：当前无法判断；
- `CONFLICT`：不同证据相互冲突。

`HYPOTHESIS` 和 `UNKNOWN` 不得写成已确认事实。核心优化若主要依赖它们，必须设计最小验证或降低优先级。

---

## 6. 候选改进比较

每个主要候选至少比较：

| 维度 | 要回答的问题 |
|---|---|
| 针对性 | 是否对应已识别的真实瓶颈？ |
| 预期收益 | 是否改善核心题目答案或关键指标？ |
| 论文价值 | 是否形成可解释、可验证的亮点？ |
| 验证能力 | 是否能通过对比、消融、回测、敏感性或鲁棒性验证？ |
| 时间成本 | 能否在剩余比赛时间内完成并复核？ |
| 失败风险 | 失败是否会破坏已有闭环？ |
| 复杂度 | 增加的代码、参数和维护成本是否合理？ |
| 回退能力 | 失败后能否恢复到已通过版本？ |

默认最多同时保留 2 个主要改进方向。超出时必须说明必要性和时间预算。

---

# 7. O1 — S2 总体方案优化

## 7.1 输入

至少读取：

- `work/01_problem_analysis.md`
- `work/02_data_audit.md`
- `work/03_requirement_matrix.md`
- `work/04_solution_plan.md`
- `work/models/` 中模型合同
- `work/05_experiment_plan.md`
- 当前 `CURRENT.md`

## 7.2 重点优化

- 是否真正回答全部小问；
- 小问间数据流和逻辑是否闭环；
- 变量、单位、目标函数、约束和假设是否合理；
- 模型输入是否真实可获得；
- Baseline 是否足够简单可靠；
- 验证设计能否支持主要结论；
- 最后一问是否可执行；
- 计算和工程规模是否适配一张 A800 与一名主要建模/代码成员；
- 是否存在更简单但同样有效的方案。

## 7.3 决策

- `PROCEED_TO_G2`：方案已足以接受 Gate 审核；
- `REVISE_IN_S2`：方向可保留，但需先修改方案或合同；
- `BACKTRACK_TO_S1`：题意或数据理解存在根本问题。

只有 `PROCEED_TO_G2` 才允许提交 G2。

---

# 8. O2 — S3 Baseline 失败诊断

## 8.1 输入

至少读取：

- 已批准的模型合同；
- `work/06_baseline_report.md`；
- `src/` 与 `experiments/baseline/`；
- `results/raw/baseline/`；
- `logs/experiments.md`；
- 当前 `CURRENT.md`。

## 8.2 诊断顺序

必须先排除：

1. 数据读取或预处理错误；
2. 数据泄漏或划分错误；
3. 指标计算错误；
4. 代码实现偏离模型合同；
5. 随机性或数值不稳定；
6. 输入信息不足；
7. 最后才判断模型能力不足。

## 8.3 重点输出

- 哪些小问已达到可用底座；
- 最重要的 1—3 个失败模式；
- 每个失败模式的证据和影响；
- S4 最多 1—2 个主要改进方向；
- 每个方向的最小验证、时间盒、成功阈值和回退版本；
- 哪些看似高级但不值得做的方向。

## 8.4 决策

- `PROCEED_TO_G3`：Baseline 闭环，S4 改进计划有证据且受控；
- `REVISE_BASELINE`：需先修复 Baseline、数据或评价问题；
- `BACKTRACK_TO_S2`：模型合同或总体方案需重构。

只有 `PROCEED_TO_G3` 才允许提交 G3。

---

# 9. O3 — S4 优化收益审计与冻结

## 9.1 输入

至少读取：

- `work/07_failure_analysis.md`
- `work/08_main_model_report.md`
- `work/09_evidence_report.md`
- 主模型、对比、消融、敏感性和鲁棒性结果；
- `logs/experiments.md`；
- 当前剩余时间与 `CURRENT.md`。

## 9.2 重点审计

- 改进是否稳定且来自公平比较；
- 是否存在测试集调参、选择性报告或只挑最好随机种子；
- 核心组件是否有足够证据；
- 主要结论是否可以安全写入论文；
- 剩余缺口是否真会改变核心结论；
- 新一轮优化是否会挤压结果冻结、绘图、写作和终审时间；
- 当前最佳模型是否已有明确版本、配置和回退点。

## 9.3 决策

- `FREEZE_CANDIDATE`：停止性能扩张，提交 G4；
- `ONE_BOUNDED_ITERATION`：只允许一个明确、限时、可回退的最终动作，完成后重新执行 O3；
- `BACKTRACK`：当前主模型或证据链存在根本问题，按报告指定阶段回退。

只有 `FREEZE_CANDIDATE` 才允许提交 G4。

---

## 10. 时间盒与停止规则

默认规则：单个优化动作若预计消耗超过剩余比赛时间的 15%，且不能明确改善核心题目答案、关键证据或论文结论，则不执行，除非用户明确批准。

满足以下任一情况应优先停止优化：

- 全题已闭环且核心结论证据充分；
- 连续尝试没有稳定收益；
- 增益只出现在少数随机种子或局部样本；
- 新复杂度明显高于其实际或论文收益；
- 无法公平验证；
- 会破坏已通过 Gate 的成果；
- 剩余时间不足以完成结果冻结、绘图、论文和最终审核。

禁止在 S5 结果冻结后继续无控制调参。确需修改时，必须记录影响并重新核验相关 Evidence。

---

## 11. 回退与版本规则

每个主要优化动作开始前必须记录：

- 当前可用 Git commit 或模型版本；
- 需要修改的文件；
- 预计完成时间；
- 成功阈值；
- 停止阈值；
- 回退方法。

失败后不得继续用无效结果覆盖已通过版本。核心方案若跨越已通过 Gate 发生变化，必须记录并按角色协议重新审核。

---

## 12. 强模型 Advisor 调用规则

建议调用节点：

- O1：独立审查总体方案和模型合同；
- O2：依据 Baseline 证据诊断最值得改进的位置；
- O3：审计证据并判断继续还是冻结。

Advisor 输出建议写入：

```text
reviews/advisor_o1.md
reviews/advisor_o2.md
reviews/advisor_o3.md
```

Advisor 不得直接改代码、接管主 Agent、无限提出新路线或替代 Reviewer 的 Gate 结论。主 Agent必须说明采纳或拒绝建议的理由。

## 14. Gate 绑定规则

Reviewer 在 G2、G3、G4 必须检查：

1. 对应优化报告是否存在且匹配当前版本；
2. 瓶颈是否由证据支持；
3. 候选是否比较了收益、验证、时间、风险与回退；
4. 是否设置成功标准和停止条件；
5. 最终决策是否允许提交当前 Gate；
6. 是否出现无依据换模型或无限优化。

对应报告缺失、版本过期、关键证据不足或决策不满足要求时，至少应判定 `REVISE`；若暴露根本问题，则按 Reviewer 规则判定 `BLOCK`。

---

## 15. 核心原则

优化必须减少一种真实风险或增强一条核心证据。不能说明“针对什么问题、如何验证、何时停止、失败如何回退”的改动，不进入正式优化计划。
